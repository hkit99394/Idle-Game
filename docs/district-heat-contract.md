# District Heat Contract

## Decision

Stage 3.1 selects **District Heat** as the next neon-native mechanic candidate after the completed Intrusion prototype.

The first implementation path is **report-only projection**. District Heat should be modeled in balance/simulator tooling before it changes live rewards, route behavior, save data, or web UI. This keeps the next prototype useful without turning one mechanic into an unbounded economy, save, and interface rewrite.

District Heat represents attention generated by repeated or risky activity in a district. The intended player fantasy is that farming, routing, and operations feel like pressure in a watched neon district rather than neutral repetition.

## Candidate State Models

| Model | Decision | Reason |
| --- | --- | --- |
| Report-only projection | Selected first. | Lets tools show heat gain, decay, and affected districts without save migration, UI promises, or live reward churn. |
| Derived runtime value | Defer. | The current game does not retain enough route/activity history to derive useful live heat without either saving history or creating confusing session-only behavior. |
| Persisted per-district heat | Defer. | Likely requires save-version migration, cloud-save contract updates, diagnostics, reset/import coverage, and UI explanation before it is safe. |

Stage 3.1 may implement report-only heat projection after the pacing and debt reviews are complete. It must not persist heat or apply live reward/risk modifiers unless this contract is amended by a later slice.

## Report-Only Heat Projection

The first projection should be deterministic and self-contained inside tooling. It should not read or write save data.

Recommended initial report inputs:

- `districtId`: the district being evaluated.
- `routeId`: the route/farm target generating pressure.
- `activityType`: `active_clear`, `offline_farm`, `boss_attempt`, or `assignment`.
- `activityCount`: repeated clears, projected offline clears, boss attempts, or completed assignment cycles.
- `elapsedSeconds`: report window length, when available.
- `clearTimeSeconds`: active simulated or target clear time used to estimate clears per window.

Recommended projected output:

- `projectedHeat`: normalized `0` to `100` pressure score.
- `heatBand`: `cool`, `watched`, `hot`, or `lockdown`.
- `gainReason`: short machine-readable reason for the dominant gain source.
- `decayReason`: short machine-readable reason for any projected decay.
- `affectedDistrictId`: canonical district id.
- `affectedRouteId`: canonical route id when route-specific.

The exact field names and export location should be finalized in the report-only slice. Until then, this contract defines the meaning and boundaries rather than a stable export schema.

## Gain, Decay, And Caps

The first report-only projection should use simple bounded scoring. These numbers are tuning defaults, not player-facing promises:

- Active route clear: `1` heat.
- Offline farm clear: `0.75` heat, because offline activity is already efficiency-reduced but can repeat for long windows.
- Boss attempt: `3` heat, because boss pushes should look riskier than routine farming.
- Assignment completion: `0.5` heat when the assignment has a district target; otherwise `0`.
- Per-route repetition bonus: add `25%` to gain after the first `20` repeated clears of the same route in a report window.
- Cap: clamp projected heat to `100`.
- Decay: subtract `10` heat per inactive projected hour for the district in report-only scenarios that model elapsed time.
- Band thresholds: `cool < 20`, `watched < 50`, `hot < 80`, `lockdown >= 80`.

These defaults are intentionally small and readable. They should be changed only through report evidence, not because a live UI needs drama.

## First Allowed Effects

No live effects are allowed in the contract-first slice.

After report-only projection proves useful, the smallest live effect should be one of:

- adjust offline farm recommendation scoring;
- show a non-punitive warning or report note before changing rewards;
- apply a small offline-only reward/risk modifier for a single district band.

Any live effect must have a separate backlog slice with focused tests, simulator evidence, and save/UI posture. Live heat should not affect active combat, boss gates, assignments, and rewards all at once.

## Save And Compatibility

Stage 3.1 report-only District Heat must not change save shape.

Rules:

- No `SaveData` field for heat.
- No `SAVE_DATA_VERSION` bump.
- No cloud-save envelope field.
- No browser storage key migration.
- No import/export normalization for heat.
- No heat state in battle records or replay/accounting payloads.

If a later milestone chooses persisted heat, it must open a dedicated save-version slice covering:

- `core/save/saveTypes.ts`;
- migrations and fixtures for every supported version;
- import/export diagnostics;
- cloud-save contract updates;
- conflict behavior when offline heat and rewards are granted during load;
- web reset and time-travel behavior.

## UI And Copy

District Heat remains a deferred mechanic in live UI until a real player-facing system exists.

Rules:

- Do not add a heat meter, route badge, onboarding copy, tooltip, or player-facing status label in Stage 3.1 unless the contract is explicitly amended.
- Keep `tests/web/displayTerms.test.ts` guarding future-only mechanic terms in live web source.
- Docs may discuss District Heat as a contract and report concept.
- If report-only tooling prints heat text, that output is author-facing and must not be confused with player-facing UI.

## Simulator And Reports

District Heat belongs first in balance tooling.

Preferred implementation order:

1. Add a small heat projection helper under `core/balance` or `tools/balance`.
2. Feed it with simulator/report data rather than live save data.
3. Print an author-facing section or opt-in report output that explains projected heat by district and route.
4. Decide separately whether stable compact JSON/CSV exports should include heat fields.

Default posture:

- `npm run simulate` may include an author-facing heat projection section after the contract/pacing slices approve it.
- Stable compact JSON/CSV exports should not gain heat columns without an explicit schema decision.
- Tactic comparison exports should not gain heat fields in Stage 3.1.
- Existing Black Iron Foundry and Redline Outpost budget debt must remain visible by stable ids in the same report run.

## Balance And Pacing Dependencies

District Heat should not become live until these questions are answered:

- Does offline farming still use fixed clear-time assumptions, or has active/offline parity been addressed?
- Which known Black Iron Foundry and Redline Outpost misses block heat, if any?
- Are heat gains based on active clears, offline clears, boss attempts, assignments, or only report windows?
- Does heat reward pressure make farming choices clearer, or does it simply punish idle play?
- Can report-only heat explain a useful next decision without creating a save migration?

## Promotion Gates

Report-only District Heat can advance to a live implementation only when all of these are true:

- The report projection exists or is fully specified.
- Offline active/parity risk is classified.
- Known balance debt is classified as blocker, deferred debt, or tuning candidate.
- Save posture is explicit: no persistence, derived-only, or a planned save-version slice.
- UI posture is explicit and tested.
- Existing simulator debt remains visible or is intentionally retuned before heat changes rewards.

Until those gates pass, District Heat is an authoring/report concept, not a live player-facing system.
